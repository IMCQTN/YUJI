# 从语料建立可解释语言档案

## 目录
1. 说话人、来源与覆盖
2. 特征层级
3. 档案结构与证据
4. 冲突和更新

## 1. 说话人、来源与覆盖

先辨认要模仿谁。其他人的话只作上下文，不能统计为目标风格。不同人同名时使用独立 persona_id；补充同一人的材料时显式沿用现有 ID，不按姓名合并。默认保留输入顺序，不假装从不完整时间戳还原真实先后。

样本数量是工作建议，不是准确率保证：

| 目标语料 | 建档方式 |
| --- | --- |
| 少于 10 条短消息 | 只能做临时声线草图；只使用明显可见特征 |
| 10–29 条 | 提取初步节奏和词汇；大部分情境规则 tentative |
| 30–99 条且有多场景 | 建立场景化档案；查看关系/主题分布 |
| 100 条以上、多场景多关系 | 可以比较局部风格；仍不能推断未知事实或内心 |

同一人只在群聊里的语料，不能证明其私聊也如此。只有正式文章时优先做文章改写；若用户要求日常聊天，说明迁移缺口并降低强度。大量相似短句不能代替多样场景覆盖。

连续多条消息构成一个回复回合时，保留上下文关系。工具的 message 长度是导出文件中的消息长度，不等同于语义回合长度；人工分析时检查是否需要合并同作者连续气泡。不要在自动统计后将所有回复机械裁剪到中位数。

## 2. 特征层级

按以下顺序分析，而非先贴性格标签：

1. 表层：句长、分句、换行、标点、英文混用、表情频率、错别字是否稳定。
2. 结构：先结论还是先铺垫；喜欢留白还是补充解释；会不会连发几条。
3. 言语行为：如何接受邀请、婉拒、道歉、拒绝道歉、表达关心、开玩笑。
4. 互动：回应重点是否贴题、如何接对方情绪、会不会反问、怎么结束话题。
5. 情境：对熟人/陌生人、忙碌/轻松、争执/日常分别如何变化。
6. 知识边界：哪些是此人明确说过的自述；哪些是用户提供的虚构设定。

不要把“经常短答”直接升级为“冷漠回避型人格”，不要把一句安慰升级为“爱你”，不要从敏感身份猜语气。允许合理的新句子；避免每轮都套“先冷淡再关心”公式。

`candidate_ngrams` 是字符二元组线索。比如“今天”高频可能只是话题，不能自动标记为口头禅。标记稳定用语前，查看多个独立场景、频率和上下文。

## 3. 档案结构与证据

先运行 profile.py init，再编辑其生成的 JSON。不要手造 schema_version、persona_id 或 train_hash。

每个规则使用下面结构；id 是唯一的，quote 必须是该训练消息中连续的原文：

```json
{
  "id": "r-comfort-01",
  "dimension": "pragmatics",
  "instruction": "安慰时先接住眼前困境，再给一个很小的实际选择；不连续追问。",
  "scope": {"scene": "comfort", "relationship": "friend"},
  "provenance": "corpus",
  "confidence": "supported",
  "evidence": [
    {"id": "替换为真实训练消息ID", "quote": "替换为原文短摘录"},
    {"id": "另一真实训练消息ID", "quote": "另一原文短摘录"}
  ],
  "exceptions": "正式场景或有紧急实际问题时可以更直接"
}
```

dimension 取 rhythm/lexicon/punctuation/pragmatics/relationship/boundary/topic/register。supported 规则至少有两条不同训练消息的引用；这只是最低引用要求，不能替代语义审查。只出现一次的模式标 tentative，表达为“当前样本中出现过”，避免硬执行。

`scope.scene=general` 为一般倾向。局部规则优先于一般倾向；用户明确纠正优先于推断规则。局部关系不匹配时不直接套用；缺少对应场景可回退到一般声线，不臆造局部习惯。

`claims` 记录人物自述，例如：

```json
{
  "id": "c-01",
  "subject": "目标人物",
  "statement": "在这段语料中说自己不喝咖啡",
  "provenance": "corpus",
  "truth_status": "corpus_statement",
  "confidence": "tentative",
  "evidence": [{"id": "真实训练ID", "quote": "我不喝咖啡"}],
  "scope": {"time": "语料对应时间，未知则填 unknown"}
}
```

自述不等于已经核实的现实事实。过去说“不喝”不能证明现在永远不喝。claims 不放“他肯定嫉妒”“其实一直喜欢你”等无从证实的推断。

`relationships` 用 id/statement/provenance/confidence/evidence/scope 结构，记录称呼和互动差异。明确用户设定使用 provenance=user、confidence=user、source_note；虚构设定用 provenance=fictional，不伪造语料引用。

`voice_summary` 是有证据规则的简短摘要，避免塞入没有规则支持的性格判断。`status` 完善后可设为 ready；validate 的真实结果才决定引用检查是否通过。

## 4. 冲突和更新

如果同一人对不同对象表达不同，不平均成一种“中间人格”。分别记关系和场景。若文本先后变化，保留 timestamp 范围；无法解释的冲突写入 limitations。

补充语料时：新目录联合重建 → 明确保留 persona_id → 重新生成 stats/train_hash → 重新核对旧引用 → 新版本档案 → validate → 明确 rebind 会话。不能只改 train_hash 让旧证据假装仍然有效。

feedback 会保存旧版档案和用户纠正。`supersedes` 精确指向被覆盖规则，且仅在反馈指定场景中覆盖；全局纠正使用 scene=general。对反馈仍需判断适用范围，不能把一次“这里少说点”升级成永久不说长句。
